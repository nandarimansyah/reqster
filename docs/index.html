Reqster

An open-source, cross-platform desktop API client for testing, debugging, and exploring HTTP/REST APIs. Built with Tauri for a fast, lightweight, local-first experience — no accounts, no cloud sync.

Get Started View on GitHub

v0.1.0   MIT Licensed  ·  Windows / macOS / Linux

Features

Everything you need for day-to-day API testing.

GET POST PUT PATCH DEL

Send HTTP requests with all major methods. URL bar with method selector and Enter-to-send.

🔧 Query Params & Headers

Key-value editors with enable/disable toggles per row. Used for both query parameters and headers.

📦 Request Body

JSON, plain text, form-urlencoded, and multipart form-data. Auto-detected Content-Type.

📄 Response Viewer

Pretty-printed JSON, raw text view, status badge with colour coding, response time, and size.

📁 Collections

Organise requests into collections and folders. Full CRUD with inline rename, duplicate, and reorder.

🌱 Environment Variables

{{variable}} substitution in URL, headers, and body. Multiple environments (Local, Staging, Prod).

🔐 Authentication

API Key (header or query), Bearer Token, and Basic Auth. OAuth 2.0 planned post-v1.

🌙 Light & Dark Mode

CSS-variable-based theming with a toggle in the header. All colours reference CSS custom properties.

⚡ Local-First

Fully offline. No accounts, no telemetry, no cloud sync. All data stored locally via SQLite.

🚀 Fast & Lightweight

Built with Tauri (Rust + webview). Significantly lower memory footprint than Electron-based tools.

Getting Started

Prerequisites

  • Node.js (LTS recommended)
  • Rust toolchain (stable)
  • Tauri prerequisites for your OS

Install & Run

# Clone the repository
git clone https://github.com/nandarimansyah/reqster.git
cd reqster

# Install dependencies
npm install

# Start in development mode (Vite + Tauri)
npm run tauri dev

Data Flow

When a user sends an HTTP request, the flow is:

User action → Component state update → Re-render
               │
               ▼
      useRequest.sendRequest()
               │
               ▼
    invoke<T>("send_request", { method, url, headers, body })
               │
               ▼
    Tauri IPC bridge (JSON serialised)
               │
               ▼
    Rust commands::send_request()
               │
               ▼
    reqwest::Client sends HTTP
               │
               ▼
    HttpResponse returned to frontend
               │
               ▼
    setResponse(data) → ResponsePanel re-renders

Data Model

TypeScript Types

type HttpMethod = "GET" | "POST" | "PUT" | "PATCH" | "DELETE" | "HEAD" | "OPTIONS";
type BodyType  = "none" | "json" | "text" | "form-urlencoded" | "multipart";

interface KeyValuePair {
  id: string;
  key: string;
  value: string;
  enabled: boolean;
}

interface RequestBody {
  type: BodyType;
  content: string;
}

interface HttpRequest {
  id: string;
  name: string;
  method: HttpMethod;
  url: string;
  queryParams: KeyValuePair[];
  headers: KeyValuePair[];
  body: RequestBody;
}

interface HttpResponseData {
  status: number;
  status_text: string;
  headers: { key: string; value: string }[];
  body: string;
  duration_ms: number;
  size_bytes: number;
}

interface Collection {
  id: string;
  name: string;
  requests: HttpRequest[];
}

Rust Structures (Backend)

// From the frontend
#[derive(Debug, Deserialize)]
pub struct HttpHeader {
  pub key: String,
  pub value: String,
}

// Returned to the frontend
#[derive(Debug, Serialize)]
pub struct HttpResponse {
  pub status: u16,
  pub status_text: String,
  pub headers: Vec<HttpHeader>,
  pub body: String,
  pub duration_ms: u64,
  pub size_bytes: usize,
}

Registered Commands

CommandDescription
send_requestBuilds an HTTP request via reqwest, sends it, and returns HttpResponse

Key Design Decisions

  • Per-request reqwest::Client — simpler than managing a static client; pooling can be added later.
  • Raw string body — Content-Type is user-set (or auto-inferred later).
  • Eager response collection — bytes converted to String via String::from_utf8_lossy.
  • Duration — measured with std::time::Instant.
  • Error handling — all errors surfaced as Result<HttpResponse, String>.

IPC Communication

The frontend sends commands to the backend via @tauri-apps/api/core invoke:

// Frontend (useRequest.ts)
const result = await invoke<HttpResponseData>("send_request", {
  method: request.method,
  url,
  headers: activeHeaders,
  body, // string | null
});

The Rust side declares:

#[tauri::command]
pub async fn send_request(
  method: String,
  url: String,
  headers: Vec<HttpHeader>,
  body: Option<String>,
) -> Result<HttpResponse, String> { ... }

Key rules: Parameter names in the TS object must match Rust function parameter names exactly. Return values are serialised to JSON by Tauri and deserialised by the generic type parameter on the TS side.

Security Model

Principles

  1. No data leaves the machine — all storage is local, no telemetry, no accounts.
  2. Sensitive values must not be logged — auth header values never reach println! or the log crate.
  3. CSP is set to null (disabled) — acceptable for a developer tool that makes HTTP requests to arbitrary URLs.
  4. Tauri v2 capability model limits what each window can do.

Threat Surface

VectorMitigation
Malicious URL in request inputreqwest validates URLs; user is responsible for targets
XSS in response body previewResponse body rendered as text in <pre>, not innerHTML
SQL injection in storageParameterised queries (rusqlite) or safe plugin API

Development is organised into phases. Here's the current status and what's planned.

Implementation Phases

Phase 0 — Local Persistence (Foundation) 0%

Everything depends on storage. No data survives a restart today.

  • Choose storage engine (rusqlite / tauri-plugin-sql / JSON)
  • Design SQLite schema
  • Rust CRUD commands for collections, requests, environments
  • Frontend persistence hooks (load on mount, auto-save)

Phase 1 — Collections CRUD 0%

  • Sidebar: New Collection, inline rename, delete with confirmation
  • Drag-and-drop reorder (or arrow buttons)
  • Context menu on request items: Rename, Duplicate, Delete, Move
  • Wire Save button / auto-save in RequestPanel

Phase 2 — Environment Variables 0%

  • Rust resolve_variables() for {{variable}} substitution
  • Environment switcher dropdown in header
  • "Manage Environments" dialog with key-value editor
  • Syntax highlight {{variable}} patterns in inputs

Phase 3 — Authentication 0%

  • Auth state model (AuthConfig type)
  • Auth tab UI with radio/forms for API Key, Bearer, Basic
  • Backend auth header injection
  • Sensitive value masking in UI and logs

Phase 4 — Body & Response Enhancements 0%

  • Multipart form-data body
  • Save response to file (native dialog)
  • Raw / pretty JSON toggle, line numbers, collapsible tree
  • Search within response body

Phase 5 — Shortcuts, Polish & DX 0%

  • Keyboard shortcuts (Cmd+Enter, Cmd+S, Cmd+N, etc.)
  • Resizable split pane, responsive sidebar collapse
  • Debounced auto-save, virtualised large responses
  • Request cancellation (AbortController + reqwest abort)
  • Vitest unit tests + Rust unit tests

Phase 6 — Future / Post-v1

  • Import / Export (Postman v2.1, Insomnia, cURL)
  • Request History ("Recent" sidebar section)
  • CLI Companion (reqster run)
  • Plugin system (wasm / Lua), pre/post hooks
  • GraphQL, WebSocket, gRPC protocols

Dependency Graph

Phase 0 (Storage)
  └── Phase 1 (Collections CRUD)
  └── Phase 2 (Environments)
        └── Phase 3 (Auth) — can start in parallel with Phase 2
  └── Phase 4 (Body & Response)
  └── Phase 5 (Polish) — can start after Phase 1
        └── Phase 6 (Future)

Phases 2 and 3 can be developed in parallel. Phase 4 can start once Phase 0 is stable.

Non-Goals (v0.x)

The following are explicitly out of scope for initial versions:

  • Team collaboration
  • Cloud sync
  • User accounts
  • Analytics or tracking
  • API mocking
  • Automated tests / collections runner
  • GraphQL client
  • WebSocket / gRPC client
